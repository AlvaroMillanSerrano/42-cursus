# call me maybe

Introduction to function calling in LLMs.

## Description

**Goal.** Translate natural-language prompts into structured function calls. Given a prompt such as `"What is the sum of 2 and 3?"`, the program does not answer `5`. Instead it outputs the function to call and its typed arguments:

```json
{
  "prompt": "What is the sum of 2 and 3?",
  "name": "fn_add_numbers",
  "parameters": {"a": 2.0, "b": 3.0}
}
```

**Overview.** Small language models (here `Qwen/Qwen3-0.6B`) are unreliable when asked to write JSON freely. This project does not rely on prompting alone: it uses **constrained decoding**, intervening at the token-selection step so the model can only choose tokens that keep the output valid and compliant with the function schema. The result is always parseable JSON with the right keys and types, even with a 0.6B parameter model.

The available functions are read from a `functions_definition.json` file, so nothing is hardcoded: the same code works with any set of functions and prompts.

## Example usage

Input functions (`functions_definition.json`):

```json
[
  {
    "name": "fn_add_numbers",
    "description": "Add two numbers together and return their sum.",
    "parameters": {"a": {"type": "number"}, "b": {"type": "number"}},
    "returns": {"type": "number"}
  },
  {
    "name": "fn_reverse_string",
    "description": "Reverse a string and return the reversed result.",
    "parameters": {"s": {"type": "string"}},
    "returns": {"type": "string"}
  }
]
```

Input prompts (`function_calling_tests.json`):

```json
[
  {"prompt": "What is the sum of 2 and 3?"},
  {"prompt": "Reverse the string 'hello'"}
]
```

Output (`function_calling_results.json`):

```json
[
  {
    "prompt": "What is the sum of 2 and 3?",
    "name": "fn_add_numbers",
    "parameters": {"a": 2.0, "b": 3.0}
  },
  {
    "prompt": "Reverse the string 'hello'",
    "name": "fn_reverse_string",
    "parameters": {"s": "hello"}
  }
]
```

## Algorithm explanation

### Generation pipeline

For every prompt the program follows the standard pipeline: prompt, tokenization, input IDs, LLM processing, logits, token selection. The token chosen is appended to the context and the process repeats. The only difference with a normal generation is the **token selection** step.

### Constrained decoding

The program never asks the model to write the whole JSON. The output is split into **fixed parts** and **slots**:

```
{"name": "«SLOT: function name»", "parameters": {"«p1»": «SLOT», "«p2»": «SLOT»}}
```

- **Fixed parts** (`{"name": "`, `", "parameters": {`, parameter names, separators) are written by the program itself. They are encoded and appended to the context without asking the model, so the structure is always correct.
- **Slots** (the function name and each argument value) are generated by the LLM token by token, but restricted to valid tokens.

At every step of a slot:

1. The model returns the logits for the whole vocabulary.
2. For each token in the vocabulary, a **judge** function receives the text generated so far for this slot (`cur`) and the text of the candidate token (`tok`), and returns one of three states:
   - `INVALID`: the token would break the structure or the schema. It cannot be selected.
   - `OK`: the token is allowed and is appended to the slot.
   - `STOP`: the token is allowed and signals that the slot is finished (for example a `,` after a complete number). It is not appended.
3. The next token is the allowed token (`OK` or `STOP`) with the highest logit. This is equivalent to setting the logits of invalid tokens to negative infinity and taking the argmax, but without building a vocabulary-sized mask.
4. If an `OK` token is chosen it is appended to the context and the loop repeats. If a `STOP` token is chosen, the slot ends.

### Judges (one per type)

| Type | Valid token if... | Slot ends when... |
|---|---|---|
| function name / boolean | generated text + token is still a prefix of one of the options | the text is a complete option and no other option extends it |
| number / integer | generated text + token is still a valid number (regex) | the number is complete and the model prefers a closing token (`,`, `}`, space) |
| string | the token does not contain `"`, `\` or line breaks | the model prefers a token starting with `"` |

### Token texts

The tokenizer vocabulary (`vocab.json`) stores tokens in a byte-level BPE representation, where for example `Ġ` stands for a space. The program reverses this mapping once at start-up to build an `id -> real text` dictionary, which the judges use to decide whether a token is valid.

### Building the output

The final JSON is never assembled as free text. Each slot result is converted to a typed Python value (`float`, `int`, `bool`, `str`), stored in a dictionary, and written with `json.dump`. This guarantees valid JSON and correct types (for example `2.0` for a `number`).

## Design decisions

- **Fixed structure, generated slots.** The model only decides what must be decided. This is what guarantees 100% valid JSON independently of model size.
- **The function is chosen by the LLM.** The function name is generated under a prefix constraint over the names in the definition file. There are no heuristics such as keyword matching.
- **Fully generic.** Function names, parameter names and types come from `functions_definition.json`. Adding a function requires no code change.
- **One judge per type.** The generation loop is the same for every type; supporting a new type only requires a new judge.
- **`Enum` for judge states.** `State.INVALID / OK / STOP` is more readable and type-safe (mypy) than loose integers.
- **Pydantic models** for the function definitions, to validate the structure of the input file.
- **No numpy in the final code.** The set of candidate tokens is small compared with the vocabulary, and `max()` over candidates is equivalent to masking with negative infinity without building a 150k-element array.
- **Scoring whole functions by probability was discarded.** It needs one model pass per token per function (slow with many functions) and it does not work for arguments, which have no finite list of candidates.
- **Only public SDK methods** are used (`encode`, `get_logits_from_input_ids`, `get_path_to_vocab_file`).
- **Errors are handled per prompt**, so a failure on one prompt does not stop the others.

The main cost per generation step is one forward pass of the model plus the judge evaluation over the vocabulary.

### Known limitations

- A function name that is a prefix of another one (for example `fn_add` and `fn_add_numbers`) is not resolved correctly.
- String values cannot contain `"`, `\` or line breaks.
- Parameter types other than `number`, `integer`, `boolean` and `string` are treated as strings.
- Tokens that are partial bytes of a UTF-8 character are discarded, so some unusual characters cannot be generated.
- Accuracy depends strongly on the prompt given to the model (`build_prompt`), especially for argument extraction with a 0.6B model.

## Challenges faced

> Adapt these to your real experience.

- **Understanding tokens, logits and constrained decoding.** Solved by experimenting step by step: encode a sentence, print the logits, and restrict the choice to a hand-picked set of tokens.
- **Byte-level vocabulary.** Tokens such as `Ġsum` do not contain the real text. A byte-to-character table is reversed to recover it.
- **Speed.** Evaluating the judge over about 150k tokens at every step is slow. Reducing the candidates evaluated and using a short prompt made the run time acceptable.
- **Dependencies with `uv`.** The SDK needs `torch`, `transformers` and `huggingface-hub` internally, so they must be declared in `pyproject.toml` for `uv sync` to produce a working environment.
- **Imports as a package.** Running with `python -m src` requires relative imports (`from .module import ...`) and `__init__.py` files.

## Testing strategy

- Run the provided example files and check that the output file exists, is valid JSON, and has exactly the keys `prompt`, `name` and `parameters`.
- Check that function names and argument types match `functions_definition.json`.
- Custom function and prompt files with functions not present in the examples (subtraction, integer and boolean parameters, several string parameters) to check that nothing is hardcoded.
- Edge cases: empty strings, negative numbers, large numbers, decimals, special characters, accented characters, ambiguous prompts.
- Error handling: missing input files, invalid JSON, empty function list, malformed function definitions.
- Static checks: `make lint` (flake8 and mypy).
- Clean install check: `rm -rf .venv && uv sync && make run`.
